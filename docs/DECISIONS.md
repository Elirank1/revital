## D-008 (agents-engine) · 2026-07-31 · Spend-cap semantics: UTC day buckets, allow-at-limit, fail-open marker, additive response fields
Wave-0 spend guard (`api/_lib/spend.ts`) counts INCR-then-compare: a call is allowed while `count <= limit`, so call N under limit N succeeds and N+1 gets the 429 — simplest boundary that never wastes a paid call on the block itself. Day buckets are UTC (`toISOString` slice) so serverless regions agree on "today"; TTL 48h self-cleans keys across the boundary. Limits come from `SPEND_CAP_CLAUDE`/`SPEND_CAP_ENRICH`/`SPEND_CAP_GEMINI` with defaults 200/40/40; invalid or non-positive env values fall back to defaults rather than disabling the cap. On Redis failure or missing `KV_REST_API_URL`/`KV_REST_API_TOKEN` the guard fails OPEN (charter mandate) and the handlers surface `spendGuard:'unavailable'` as an additive field on their success JSON (including the Anthropic passthrough in `api/analyze.ts` — clients ignore unknown top-level fields, so flag-off behavior stays byte-identical whenever Redis is healthy). 429 bodies carry an English `error`, a Hebrew `message`, and a `spend:{service,count,limit}` object. The spend key uses the access code verbatim (matches the existing `revital:data:${code}` pattern); empty code buckets as `default`, same as `api/data.ts`.

## D-013 (platform-data) · 2026-07-31 · Version semantics: blob-level vCounter, v=0 = never-synced, equal-v POST wins, merge logic single-sourced with an inlined server copy
LWW ordering uses one monotonic `vCounter` per blob (not per record): simpler, strictly ordered, and any accepted write anywhere advances it — per-record counters add nothing under a single-blob store. Client-created records carry `v: 0` (never synced); an edit keeps the record's last-pulled server `v` as its implicit base. Server rule: `incoming.v >= stored.v` ⇒ apply + stamp `++vCounter`; `incoming.v < stored.v` ⇒ drop as stale (server wins; client converges on next GET). Equal-v accepts are intentional: they mean the client has seen the latest server state, and they are what makes one-click undelete possible (a client that has *seen* a tombstone at v=N may POST an undeleted copy at v=N). Stale live copies can never resurrect newer tombstones — unit-tested. The algorithm is single-sourced in `src/lib/persistence/merge.ts#serverMergeCollection` (15 unit tests) and inlined verbatim into the api-data-v2 proposal with a `KEEP IN SYNC` marker, because the serverless function must stay self-contained rather than importing from `src/` through the Vercel bundler. POST responses echo `{vCounter, accepted, staleDropped, records}` so the client adopts server-stamped versions without an extra GET.

## D-020 (platform-data) · 2026-07-31 · Contract semantics: duplicateOf on both dedupe kinds, addDeal throws on unknown person, creation skip-events, undo keeps server v
Autonomous calls inside the binding signatures. (1) `addPerson` returns `duplicateOf` for BOTH dedupe outcomes: exact hit ⇒ `person` is the existing record merged additively (existing fields win, missing ones filled, analysisIds unioned) and `duplicateOf` is the pre-merge copy; name-only ⇒ `person` is NEW, `duplicateOf` is the collision, and one pending `merge_person` Suggestion is filed (guarded against duplicates so re-runs stay idempotent). (2) `addDeal` THROWS on an unknown/tombstoned `personId` — that is API misuse by a programmer, unlike Rejected-without-reason which is a user-flow refusal and returns null from `moveDeal` (D-014). `addDeal` with an existing deterministic id is an idempotent no-op returning the existing deal (screener/backfill re-runs). (3) Every `addDeal` logs a creation StageEvent (`from: null`); entry at a later pipeline stage records all earlier stages as `skippedStages` so conversion stats exclude intervals the deal never sat in. (4) Undo: in-memory stack (cap 20, not persisted — a same-session affordance behind a 6s toast); restore keeps the CURRENT record's `v` so an undo after a sync round is an ordinary LWW edit, never a stale write; undoing a move appends a compensating StageEvent (`actor: 'system'`, `reason: 'undo'`) so history stays append-only. (5) `moveDeal` to `Bench` benches the Person like `Rejected` does, so `benchPersons()` is truthful for both rails.
